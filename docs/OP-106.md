# OP-106: Map LRT elevators to the walking network

Purpose: when the City reports an elevator out of service, keep routes from
using that elevator. If its exact map match is unknown, keep the original
station warning in the route report.

This is preparatory work for [issue #34](https://github.com/tatsatshah05/NatHacks2026/issues/34).
**OP-106 is not complete:** OP-104 is available in `op-104-walking-network`
(tested at `f4ef91b`) but is not merged into this base. None of the 32 recorded
City elevators has an independently reviewed device-level OSM match yet.

## Files

- `cloud/app/elevator_mapping.py`: inventory validation, review checks and the
  helper that identifies blocked elevator edge indices.
- `cloud/tests/test_elevator_mapping.py`: OP-106 tests, using recorded City
  device metadata and explicitly synthetic OSM references/route graphs.
- `cloud/tests/test_elevator_network.py`: tests against OP-104's actual network
  implementation, including zero-weight removal in both directions, recovery
  and a smoke test loading its committed Edmonton network. This module skips
  when OP-104 is absent.
- `scripts/elevator_candidates.py` and `docs/elevator-candidates.json`: a
  reproducible review aid derived from the real OP-104 file and City station
  coordinates. It does not activate matches.
- `docs/elevators.proposed.json`: one entry per City elevator, with station,
  location and an explicit reason it is currently unmapped.
- `cloud/tests/fixtures/elevator_mapping/`: the recorded master list and its
  source/capture metadata. Master-list status is not used as live outage status.

matches, write configuration, or modify the walking network.

Run all OP-106 tests with `python -m pytest cloud/tests -q`. For integration
verification before OP-104 merges, include a checkout of its branch on
`PYTHONPATH`; the namespace package then exposes `cloud.app.network` from that
dependency. The local run used a separate read-only dependency checkout rather

## Real network candidate report

The captured OP-104 network reports 9 elevator nodes and 4 elevator edges across
Edmonton. The City snapshot contains 32 LRT elevators. The generated report
contains nearby tagged objects for four City devices (Corona and Century Park),
and nearest station-point proxy nodes for review. **These are not matches.**
Several City devices can have the same station coordinates; proximity cannot
identify which physical elevator a node represents.

The 200 m radius is only a configurable search aid. Node distances are measured
to official station points; way distances use approximate endpoint midpoints.
The report records the network SHA-256 and manifest, source station stop IDs,
object URLs, distances, attribution and an explicit unreviewed label. Every
proposal entry remains unmapped with a reason based on this actual coverage.

Regenerate after OP-104 is present:

```powershell
python scripts/elevator_candidates.py --network cloud/data/network.npz --devices cloud/tests/fixtures/elevator_mapping/devices.json --stations cloud/tests/fixtures/elevator_mapping/stations.json --out docs/elevator-candidates.json
```

OP-104's notes suggest an entrance/platform fallback where elevator objects are
missing. The nearest-node proxies here have not been verified as entrances or
platforms. Agree and review that fallback with Tatsat before activating it;
an ordinary nearby street node must not silently become an elevator match.

## Proposed review format

Shared configuration needs the lead's agreement under AGENTS.md. The proposal
therefore stays in `docs/`; this PR does **not** create `config/elevators.json`
or change any shared schema/API. Agree the final format with Tatsat before
moving reviewed entries into the shared configuration required by the story.

Each elevator has a `device_id`, `station`, `location`, `status`, `osm_refs`,
`reason`, `matched_by`, `reviewed_by` and `evidence`:

- `unmapped`: no OSM references or claimed reviewers; a reason is required.
- `candidate`: references, matcher and evidence are recorded; another person
  still needs to check the match. Candidates do not change routes.
- `reviewed`: references, evidence and a second named reviewer are required.
  The matcher and reviewer must differ. These fields record review; they do
  not authenticate identities or replace a teammate's actual review.

References record both `type` (`node` or `way`) and positive integer `id`.
OSM's [element model](https://wiki.openstreetmap.org/wiki/Elements) and
[`highway=elevator` guidance](https://wiki.openstreetmap.org/wiki/Tag:highway%3Delevator)
describe the source objects. Do not use station coordinates from OP-105 as
proof of a particular elevator entrance. Each real match needs location/level
evidence and a second person's check.

The audit requires coverage of every elevator in the supplied City snapshot.
It rejects duplicate/unknown devices, mismatched station metadata, invalid OSM
IDs, self-review and a reviewed object assigned to different City devices.
When the City inventory changes, update the proposal and review the new data.

## Connect to OP-104 and OP-105

1. **OP-104 (#32):** merge its network implementation. The provided
   `network_elevator_edges(network)` adapter uses its published `NODE_ELEVATOR`
   and `EDGE_ELEVATOR` flags and original OSM IDs to build a small edge index.
   It does not modify the network format or replace the compact SciPy graph.
2. Match each City device to the correct OSM node/way. Keep devices without a
   reliable match explicitly unmapped with the real reason (for example, an
   elevator absent from OSM). Review the candidate report and update the reason
   as evidence becomes available. Have a second teammate review every match.
3. **OP-105 (#33) / OP-101 (#29):** pass current active canonical obstruction
   dictionaries from the store to `block_elevator_outages()`. Shared models can
   be converted with their normal dictionary export; this helper does not
   redefine the obstruction contract or its freshness rules.
4. Apply `masked_edge_weights(network, blocked_edge_indices, profile_weights)`
   **before each profile's route search**, then pass the result to
   `network.length_matrix()`. OP-104 drops zero weights from both adjacency
   directions. Node elevators close paths through that flagged node; way
   elevators close that physical edge. Other station paths stay available.
   Rebuild the mask when outages change so a working elevator is usable again.
5. Preserve every `station_warnings` entry in the report. It carries the original
   obstruction (including station geometry/detail) and the reason routing could
   not fully apply the outage. Reviewed references absent from the network also
   produce warnings, even when other references matched.
   The report must also retain the ordinary station-level obstruction for a
   successfully matched outage; masking a route edge does not remove that item.
6. Run an outage/recovery integration test on the real network for all four
   profiles, the full `make test`, and the preview deploy. Get Tatsat's review
   and approval before merge.

Route-change tests use synthetic device matches and graphs through the actual
OP-104 implementation. A separate smoke test loads the real committed network.
These checks do not certify any physical elevator-to-OSM correspondence.
Local runtime tests use the available Python 3.14; Python 3.12 runtime CI is
still required. The full Makefile/application is not on this base yet.

in the eventual PR into `main` to apply GitHub's automatic issue closure, or
