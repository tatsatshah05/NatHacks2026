# OP-305: Replay mode

For [issue #60](https://github.com/tatsatshah05/NatHacks2026/issues/60), targeting `phase_3`. Replay lets the demo run on recorded real data from every source when the live weather or the City feeds do not cooperate, and it is always labelled as a replay.

## Record a snapshot

```bash
make record                                   # every source into snapshots/<UTC time>/
make record RECORD_FLAGS="--cameras-from https://openpath-api-w6ql.onrender.com"
python scripts/record_snapshot.py --out snapshots/demo --weather-archive 2025-11-05
```

`scripts/record_snapshot.py` fetches each source in `config/sources.json` once, through the same official API queries the live adapters send (it runs the adapters' own readers, so the queries cannot drift apart). It writes them in the layout replay mode reads, one sub-folder per source as in `cloud/tests/fixtures/`, so the folder is a drop-in `REPLAY_SNAPSHOT`:

| File | Source |
| --- | --- |
| `lrt/outages.json`, `lrt/devices.json`, `lrt/stations.json` | LRT outages, device list, stations (`snws-u3zx`, `javh-pjj2`, `fhxi-cnhe`) |
| `city_advisories/snow.json`, `city_advisories/trails.json` | 311 snow complaints (`9i6v-cqzn`), trail closures (`k4mi-dkvi`) |
| `construction/permits.json` | Pedestrian-affecting permits active today (`7wiq-4rgy`) |
| `snow_clearing/na.json` | Snow and ice clearing routes (`8pdx-hfxi`) |
| `traffic_disruptions/current.json` | Active traffic disruptions (`k4tx-5k8p`) |
| `weather/eccc.json`, `weather/open_meteo.json` | Blatchford observation and Open-Meteo forecast, or an archive night (below) |
| `cameras/readings.json` | `GET /api/cameras` of a live API (`--cameras-from`): labels, scores and times only |
| `manifest.json` | `recorded_at`, `replay_at` (where a replay clock starts), each file's URL, row count, size and SHA-256, each source's status, and an offline replay check |

Rules the recorder keeps:

- **No images, ever.** Only JSON responses are stored; anything else (an image, an HTML error page) is refused and the source is reported as failed. Camera readings are copied from the API, never frames.
- **No secrets.** The Socrata token (`--token`, or `SOCRATA_APP_TOKEN` from the shell) is sent as the `X-App-Token` header and never written; the manifest only says whether one was used. Without a token, City reads are anonymous.
- **Honest failures.** A source that fails is listed in the manifest with its error, the others still record, and the command exits with 1.
- **One fetch per source**, every page of it, with no retries beyond what the adapter itself does.
- The data files are compact JSON. A full recording on November 8, 2026 was 8.9 MB, and `snow_clearing/na.json` alone was 6.3 MB, over CI's 5 MB file limit, so `snapshots/` is in `.gitignore` and recordings stay on the demo laptop. Record one before the demo with the commands above.

Measured on November 8, 2026 at 15:55 UTC, anonymously: 6 LRT outages, 73 devices, 54 stations, 0 open 311 snow complaints in the last 72 hours, 60 trail notices (46 active items), 1,316 permit rows (1,218 items), 222 snow-clearing routes (0 items: no snow event), 270 traffic disruptions (73 items), the Blatchford observation (5.1 °C, watch inactive) and 0 camera readings from the deployed API. The run took about 8 seconds.

## Serve a snapshot

| Setting | Behaviour |
| --- | --- |
| `DATA_MODE=replay` and `REPLAY_SNAPSHOT=<folder>` | Every adapter reads the folder through a fake HTTP transport; nothing touches the network |
| `REPLAY_AT=<ISO time with zone>` | Freezes the app's clock at that instant (unchanged from #136) |
| `REPLAY_CLOCK=running` | Starts the clock at `REPLAY_AT`, or at the snapshot manifest's `replay_at`, and advances it in real time from app start, so freshness (`age_s`) grows and items expire as they would live |
| `REPLAY_CLOCK=frozen` | Freezes at the manifest's `replay_at` when `REPLAY_AT` is not set |
| `WEATHER_REPLAY=<name>` | Serves the weather recording in `weather/<name>/` instead of `weather/` |

One clock (`app.state.clock`) drives the scheduler, the map (`GET /api/obstructions`), route hazards, the camera readings (`GET /api/cameras`) and the weather replay. The running clock counts on the monotonic clock, so a laptop clock change cannot make replay time jump. Recorded camera readings are loaded into the camera store at startup with `mode` set to `replay`, keeping their recorded times, so they show only while the replay clock is inside their lifetime.

For a recorded snapshot:

```bash
DATA_MODE=replay REPLAY_SNAPSHOT=snapshots/demo-2026-11-08 REPLAY_CLOCK=running \
  .venv/bin/python -m uvicorn cloud.app.main:app --port 8000
```

`make dev` is unchanged: it sets `DATA_MODE=replay` and `REPLAY_SNAPSHOT=cloud/tests/fixtures` and no clock settings, so it runs on the real clock as before. It passes other variables through, so `WEATHER_REPLAY=freeze_thaw make dev` shows the freeze-thaw night.

## The freeze-thaw night

`python scripts/record_snapshot.py --weather-archive YYYY-MM-DD` records a real past night from [Open-Meteo's historical weather API](https://open-meteo.com/en/docs/historical-weather-api) (`https://archive-api.open-meteo.com/v1/archive`, ERA5 reanalysis) for `WEATHER_LAT`/`WEATHER_LNG` (default 53.57, -113.52), with hourly `temperature_2m`, `dew_point_2m`, `precipitation` and `soil_temperature_0_to_7cm`, in UTC. The date is the local day the night begins on; the request covers that day and the next in UTC. The recorder runs the black-ice rule over every hour, refuses a night on which the watch never fires, and writes `weather/open_meteo_archive.json` unchanged plus `weather/manifest.json` with the active hours and the demo hour.

Environment Canada's real-time observations are kept for about 30 days (on November 8, 2026 the oldest Blatchford observation was from October 10, 2026), so a past night uses the archive for air and dew point as well as ground temperature and history. The archive has no 0 cm surface value, so the 0 to 7 cm soil layer average stands in for `ground_c`; the manifest says so.

**The committed night is November 5 to 6, 2025 in Edmonton** (`cloud/tests/fixtures/weather/freeze_thaw/`, recorded November 8, 2026). Rain began on the evening of November 5 (the first wet hour ends at 01:00 UTC on the 6th, 18:00 MST; Open-Meteo precipitation is the preceding hour's total) and the air cooled from 4.6 °C through the night. These are the archive values around the freeze, with the rule's inputs:

| UTC (MST) | Air °C | Dew point °C | Ground °C | Rain last 6 h mm | Max air last 12 h °C | Watch |
| --- | --- | --- | --- | --- | --- | --- |
| 10:00 (03:00) | 0.5 | 0.1 | 0.8 | 1.7 | 4.2 | inactive: air and ground above 0 |
| 11:00 (04:00) | 0.5 | 0.2 | 0.8 | 2.9 | 3.9 | inactive: air and ground above 0 |
| **12:00 (05:00)** | **-0.1** | **-0.4** | **0.2** | **3.5** | **3.0** | **active** |
| 13:00 (06:00) | -0.2 | -0.5 | 0.2 | 3.7 | 2.6 | active |
| 15:00 (08:00) | -0.6 | -0.9 | 0.2 | 3.9 | 2.2 | active |
| 18:00 (11:00) | 0.0 | -0.7 | 0.2 | 1.7 | 1.2 | active |
| 19:00 (12:00) | 0.2 | -0.7 | 0.2 | 1.5 | 0.9 | inactive: thawed |

At 12:00 UTC (05:00 MST, November 6) the air is at or below 0 °C, and all three triggers hold: 3.5 mm of rain in the last 6 hours, air above 0 °C in the last 12 hours (3.0 °C), and air within 1 °C of the dew point (0.3 °C apart). The watch stays active from 12:00 to 18:00 UTC (05:00 to 11:00 MST). The rule also fires briefly on November 5 (11:00 to 13:00 and 17:00 to 20:00 UTC) from frozen ground after a mild day, with no rain; the manifest lists those hours too. The demo hour is the first active hour after rain, 12:00 UTC.

The weather replay serves the archive hour the app's clock points at. When the clock is outside the night (for example `make dev` on today's clock), it serves the demo hour. `observed_at` is always the real archive hour (`2025-11-06T12:00:00Z`), never the current time, and `mode` is `replay`. To walk through the night: `REPLAY_AT=2025-11-06T11:00:00Z REPLAY_CLOCK=running WEATHER_REPLAY=freeze_thaw` (the City items in the fixtures then sit outside their dates, which is why the weather replay holds its own demo hour by default).

## Replay is never presented as live

| Endpoint | What says replay |
| --- | --- |
| `GET /health` | `"mode": "replay"` |
| `GET /api/status` | `"mode": "replay"`; each source's `age_s` is measured on the replay clock |
| `GET /api/weather` | `"mode": "replay"`, with the recorded `observed_at` |
| `GET /api/cameras` | every feature's `properties.mode` is `"replay"` |
| `GET /api/obstructions` | `generated_at` is the replay clock's time |

`GET /api/route` has no data-mode field. PLAN.md section 10 lists `mode` there as the travel mode (`walk` or `walk_lrt`), so a data-mode field would be a contract change for the lead. Routes use the same replay clock for their hazards.

**The Replay badge** (built in the design-foundation branch as `ModeBadge`, not here) reads `GET /health` and shows the badge on every page whenever `mode` is `"replay"`. It should also treat a failed `/health` request as unknown rather than live. `/api/weather` and `/api/cameras` carry `mode` too, so a weather or camera panel can label itself without a second request.

## Tests

`cloud/tests/test_record_snapshot.py` runs the recorder against a mock transport: the layout and manifest, a recording replaying offline, a failing source that does not stop the others, JSON only (an image response is refused and nothing is written), the token sent but never written, the archive request and its refusal of a night without a watch. `cloud/tests/test_replay_mode.py` covers the running and frozen clocks, expiry on the running clock, the freeze-thaw values and active hours, the `WEATHER_REPLAY` switch, recorded camera readings re-labelled `replay`, and `mode` on `/health`, `/api/status`, `/api/weather` and `/api/cameras` with the scheduler running.
